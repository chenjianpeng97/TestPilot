# 测试单步骤级执行记录（testsheet-step-record）

> 自动或半自动执行测试单时，用例卡在哪一步、为什么卡、缺什么才能继续，要写在**本轮 `testcase/` 副本里对应步骤下面**。
> `testsheet.md` 的「实测记录」只留一句摘要，细节在副本。
> 校验：`uv run tuner-testreport stats assets/testsheet/<轮次> --check`。

## 1. 写在哪

只写在 `assets/testsheet/<轮次>/testcase/<模块>/<套件>/<用例ID>.md`（本轮副本）。
用例库 `assets/testcases/` 里的文件**不写**执行记录。

副本的正文（摘要、前置条件、测试数据、步骤的「操作」「预期」）按原样保留。执行记录只追加在每个 `### N` 步骤块里「预期」的后面。
只有步骤本身有误（不是产品问题）时才改「操作」「预期」，并在 `testsheet.md` 的实测记录说明。

## 2. 格式

```markdown
### 2

- 操作：点击登录
- 预期：进入首页
- 执行：阻塞
- 实际：点击后页面一直转圈，约 30 秒后提示网络错误
- 卡点：POST /api/login 返回 502，没法进入首页，后面的步骤都无法执行
- 缺少：后端服务恢复；或绑定后端日志通道后再判断原因
- 证据：evidence/Login-open-step2.png、evidence/Login-open-step2-network.json
```

| 字段 | 取值 | 何时必填 |
| --- | --- | --- |
| `执行` | `通过`、`失败`、`阻塞` | 执行过的步骤都写。没执行到的步骤不写这几行 |
| `实际` | 看到的现象、文案、单号、状态 | `失败`、`阻塞` 必填 |
| `卡点` | 卡在哪里、为什么，写具体：哪个动作、哪个接口、哪个页面元素、返回了什么 | `失败`、`阻塞` 必填 |
| `缺少` | 缺什么才能继续：环境、数据、账号、权限、后端日志通道、预期规则…… | `阻塞` 必填 |
| `证据` | 相对测试单目录的路径，多个用顿号或逗号分隔 | 可选；写了路径就要存在 |

字段名、顺序固定，每个字段一行，写在行内，续行缩进即可。不写密码、token、Cookie；账号只写 `account_id`。

`失败` 是产品行为与预期不符；`阻塞` 是执行不下去，没法判定通过还是失败。分不清时按「能不能给出通过或失败的结论」判断：给不出就是阻塞。

## 3. 与用例结果的对应

| 用例「结果」 | 副本里至少要有 |
| --- | --- |
| 通过 | 不要求；写了的话每步都应是 `通过` |
| 失败 | 至少一步 `执行：失败`，带 `实际`、`卡点` |
| 阻塞 | 至少一步 `执行：阻塞`，带 `实际`、`卡点`、`缺少` |
| 忽略 | 不写步骤记录；`testsheet.md` 的实测记录写原因（必填） |
| 空（待执行） | 不写 |

`testsheet.md` 的「实测记录」同步写一句摘要，例如：`第 2 步阻塞：登录接口 502，详见副本`。

## 4. 校验

`tuner-testreport stats --check` 报错（`error`）的情况：

- `step_record_status`：`执行` 的值不在 通过 / 失败 / 阻塞，或写了 `实际`、`卡点` 等字段却没有 `执行`。
- `step_record_blocker`：`失败`、`阻塞` 的步骤没有 `卡点`。
- `step_record_actual`：`失败`、`阻塞` 的步骤没有 `实际`。
- `step_record_missing`：`阻塞` 的步骤没有 `缺少`。
- `step_record_missing_case`：用例结果是 失败 / 阻塞，但副本里没有带 `卡点` 的 失败 / 阻塞 步骤。

告警（`warn`）：`step_record_evidence` 证据路径不存在。

## 5. 报告里怎么用

`stats` 的 JSON 里，每条用例的 `steps[]` 带 `status`、`actual`、`blocker`、`missing`、`evidence`；
`not_run_notes[]`（阻塞、忽略、待执行）带 `blockers[]`（步骤号、状态、卡点、缺少、证据），出报告时直接引用，不用再人工翻副本。
